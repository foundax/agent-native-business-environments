# 工程设计：把复杂业务系统转化为 Agent 的执行环境

[English](design.md) · [返回项目介绍](../README.zh-CN.md)

本文档探讨如何将复杂业务系统转化为 Agent 的执行环境。本仓库是独立编写的教学参考，不映射 Foundax 的私有商业代码或真实数据模型。

## 1. 先建立系统边界

用户给出的是目标，而不是预先排好的接口调用序列。执行环境需要支持发现、创作、修改与反馈，同时保留业务系统对权限、规则和写入状态的所有权。本项目将复杂度分配到三个层次：

```text
Agent 与工具环境
  用户目标 / 任务状态 / 普通代码 / 素材像素 / 浏览器观察
             │ 按需读取、业务命令、结果回执
             ▼
业务能力层
  领域目录 / 操作契约 / SDK 投影 / CLI / 结构化错误
             │ 现有领域服务的授权调用
             ▼
业务宿主
  权限与范围 / 数据关系 / 计价与校验 / 事务与版本 / 审计
```

生产中的授权由宿主身份与会话决定，不能采信 Agent 提交的租户 ID。

本仓库实现了一个固定店铺的本地宿主，使用 Node.js 单进程与 JSON 文件模拟持久化；请求中没有租户选择字段。它展示契约分工，环境内没有模型调用、内置 Agent
Loop、自动上下文压缩、生产授权隔离或完整编辑器。

文件也有不同职责边界：`src/` 是宿主逻辑，`sdk/` 是调用接口，`fixtures/` 是合成的初始状态；`.local/site/`
是可以编辑的页面；`.local/business.json`
是宿主维护的业务状态。页面源码与业务版本分开演进。本地目录可写不意味着具备生产业务的写入授权。

## 2. 从业务资产到可组合能力

### 对象关系必须进入契约

在本例中，商品引用售后政策与媒体；促销引用商品；活动引用商品、配送政策与促销。模型可以通过 ID 建立关系，宿主可以检查关系。读写字段使用同一套名称，避免读取为一种含义、写入又需要猜另一种映射。

这些接口不必暴露数据库的全部结构。契约应回答：对象是什么、关系是什么、哪些值可写、如何表达单位、错误如何修复。例如
`priceMinor` 是 GBP 的整数便士，不是格式化字符串；国家代码是 `GB`，不是页面里的展示文案。具体契约见
[catalog](domains/catalog.md)、[fulfillment](domains/fulfillment.md) 和 [campaigns](domains/campaigns.md)。

### 生成数据与写入数据是不同责任

Agent 可以根据商家提供的信息生成标题、描述和关联计划。宿主负责字段、引用、金额和版本校验。本例的 `apply`
在候选状态中处理操作，完成检查后一次保存，因此商品可以引用同一提交中新建的对象。任何商品或促销的引用错误都会使整次提交失败。

活动允许保存不完整草稿。比如配送政策存在但国家不匹配，草稿仍可保存，`check`
会报告该缺口，活动视图和下单操作会被阻止。这样“暂存创作过程”和“满足交易前提”具有不同的语义。生产接入应根据领域决定哪些不变量必须立即成立，哪些条件在发布或执行时检查。

完整对象替换是此例的写入语义，不是通用补丁语言。`expectedRevision`
防止旧计划覆盖新状态，但整店版本会让无关变更也产生冲突。大规模系统可以使用实体版本和事务边界；跨服务时还需要处理补偿与部分成功。

### SDK 不是只有接口别名

`campaignView`
提供面向任务的读取模型，将商品、优惠、配送、售后和媒体组合成一次返回。它减少的是调用方需要反复执行的领域关联和规则计算，而不只是函数名长度。

页面可以自由调整构图，但价格展示与下单计算来自同一业务实现。下单只接收产品、数量、目的地和版本前提，金额由宿主重新计算。页面在加载或显式刷新时读取当前数据，没有自动轮询；订单记录保留成交时的售后政策与模拟价格，后续页面则继续读取当前业务状态。

这种投影也有成本：它针对活动页面的任务，需要维护语义和版本，可能隐藏其他任务需要的信息。因此底层领域读取仍然存在。不要用一个巨大 SDK 返回值覆盖所有业务场景。

## 3. 在有限上下文中逐步建立业务理解

### 目录先行，数据按需

`catalog`
只返回领域用途、契约路径和依赖。Agent 可以先理解相关对象，再读取具体契约和数据。示例的全量领域读取适合小数据；生产系统应增加分页、过滤和清楚的覆盖范围，不能把截断结果伪装成全集。

多次读取可能跨越业务版本，因此每个数据回执都包含
`revision`。本例没有跨多次读取的快照事务：如果关联读结果属于不同版本，应重新读取相关数据；宿主最终仍在最新状态上校验写入。不可变快照与按域刷新另见
[Agent Business Workspace](https://github.com/foundax/agent-business-workspace)。

### 把任务状态与原始历史分开

当前目标、已确认的事实、待解决的问题、业务版本、源码状态与最新观察，应该能够被明确区分。旧的截图可能属于已修改的页面，旧工具输出可能描述已失效的库存；它们仍有审计价值，却未必适合每轮重复送入模型。

下面是设计伪代码，不是仓库内置的上下文管理器：

```python
def prepare_model_context(task, state, history):
    context = [task.user_goal, task.constraints, state.pending_decisions]
    context += state.selected_contracts
    context += current_data_receipts(state.business_versions)
    context += current_source_references(state.source_revision)
    context += current_visual_observations(state.source_revision)
    context += history.retrieval_index()
    return fit_to_input_budget(context, preserve=task.user_messages)
```

历史索引需要可恢复的原始记录；裁剪不能把工具调用和结果拆散，也不能默默丢弃用户约束。摘要会丢失信息，检索会增加调用成本，判断“已过期”也需要版本依据。它们是需要设计与验证的机制，不是一句“自动压缩上下文”就能解决的问题。

## 4. 让创作使用熟悉的代码

这个包使用普通 HTML、CSS 和 JavaScript，没有页面 DSL。选择浏览器原生代码降低了特有协议的表达负担；同样的业务客户端也可以进入 React 或 TypeScript 项目中。

生产级的编辑器需要另行处理 AST、值来源、组件实例语义与版本，不应要求模型手工维护内部标识。身份映射、商家修改与源码重写的协同见
[Agent Editable UI](https://github.com/foundax/agent-editable-ui)。本包没有内置编辑器实现。

本例中，商品名称与价格属于业务系统，Hero 文案、构图与样式属于页面。活动标题是业务元数据，不强制等于 Hero 标题。明确所有权，才能讨论修改某个字符串的含义。页面没有把业务数据复制成只用于展示的常量。

## 5. 设计知识、媒体与模板

### 设计目标连接业务目标

在此场景的用户旅程中，顾客先理解商品，再看到优惠和购买条件，最后做出决定。模板中的大留白、视觉层次和实用信息区，都服务于这一路径。如果换成复杂规格的工业品，信息结构需要改变，不能只替换颜色与图片。

模板通过 [TEMPLATE.md](../template/TEMPLATE.md)
解释设计意图、可变部分与业务绑定。这使参考资产同时传递“结果”和“改编依据”。模板也可能造成风格趋同，因此任务要求说明至少一项适合当前需求的设计修改，而不是把保持模板原样当成成功标准。

### 媒体元数据与像素是互补信息

素材清单提供 ID、路径、尺寸、透明背景、用途和构图说明；真实像素帮助判断主体与裁切。此例使用明确标注的合成矢量图，没有商品摄影或图片生成服务。Agent 可以用已有视觉工具打开素材；不能仅因为拿到了图片 URL 就声称已观察画面。

生产中媒体分析可以前置成稳定资产元数据，减少重复查询；描述仍可能不准确，素材变更后需要失效处理。缺少合适素材时应提出需要补充的内容，而不是虚构已有图片能满足要求。

## 6. 用不同反馈回答不同问题

| 反馈层              | 能够回答                               | 不能据此推出                         |
| ------------------- | -------------------------------------- | ------------------------------------ |
| JavaScript 语法检查 | 文件能否被解析                         | 浏览器执行成功、布局好看。           |
| 领域写入校验        | 字段、引用和版本是否满足写入条件       | 草稿已经满足所有上线条件。           |
| 活动检查与 SDK 视图 | 配送、促销、商品等已实现规则是否满足   | 税务、真实支付或所有业务规则已完备。 |
| 模拟订单            | 服务端计价、库存扣减和本地保存是否协同 | 已发生真实支付或履约。               |
| 浏览器与视觉观察    | 当前尺寸下的呈现和实际执行的交互       | 所有尺寸、语言与无障碍场景都已通过。 |

反馈应包含可定位的原因。例如 `shipping_coverage`
把错误指向业务关系，比让模型从“页面打不开”反推整个服务链更容易采取行动。错误信息不能替代领域文档，也不应返回未授权的对象详情。

质量与性能的取舍需要明确对象：

- **按需读取**减少初始上下文，但增加发现步骤；常用入口可以提前给出，完整文档保留检索能力。
- **组合 SDK 视图**减少网络往返与重复关联，但需要投影维护，并可能读取当前任务不需要的字段。
- **模板复用**减少重复创作，但需要判断业务、素材和风格是否适配。
- **视觉反馈**能发现语法检查看不到的问题，但有时间与上下文成本。当视口、数据、交互状态或源代码发生变化时，可能值得重新进行视觉观察。
- **当前状态替换过期上下文**减少重复输入，但必须保留原始记录及可恢复路径。

建议记录读取字节、累计输入量、调用次数、准备耗时、首个可用预览时间和修复轮次。同时记录作品是否满足业务、交互与视觉要求。不能只用 token 下降或工具调用减少来证明质量提高。此仓库没有运行模型对照实验，也不把 Foundax 历史运行指标当作本例的测试结果。

## 7. 开放 CLI 与外部工具环境

内部 Agent、外部 Coding
Agent 和开发者可以使用同一份业务契约。仓库客户端既能被脚本导入，也能被 CLI 包装；页面通过同一 HTTP 宿主获取组合视图。工作区文件是普通源码，因而外部工具可以直接搜索、修改、预览和检查。

开放后的收益取决于实际工具能力：浏览器可以操作页面，视觉模型可以理解图像，computer
use 可以补充其他交互，但这些能力并非所有 Agent 都具备，也不保证自动产生更好的设计。本包提供共同的业务与项目接口，演示如何接入；它不捆绑模型或特定 Harness。

这也形成接口设计的检验方式：如果外部 Agent 必须获得大量未写入文档的内部知识才能工作，说明某些关系、默认值或执行反馈还没有被清楚表达。

## 8. 从参考实现接入实际系统

保留对外契约的含义，将模拟存储替换为受授权的领域服务。生产写入需要事务、审计、幂等与并发控制；单个 JSON 文件和整店版本只表达本例的机制。当前下单不自动重试，网络结果不确定时也不能盲目重发。

代码执行环境需要真实隔离，不能把 `.local/`
当成沙箱。业务权限需要在宿主逐次校验，浏览器访问域、网络出口和密钥要有各自边界。前端的模拟客户端可以提交计划，是本地单用户教学环境的选择；真实商店访客不能继承管理权限，管理与消费者接口必须分开授权。

最后分别管理业务状态、页面源码与发布版本。编辑页面文件、业务检查成功、预览可用和网站发布，是不同的结果。这个包止于本地体验；它提供可复用的职责划分与实验材料，不会把本地成功标成生产上线。
