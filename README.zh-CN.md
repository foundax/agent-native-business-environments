# Agent-Native Business Environments

## 从生成页面到交付业务：复杂业务系统中的 Agent 产品与工程实践

> **让 Agent 组织目标与创作，让业务系统提供清晰的能力、可靠的规则和可验证的反馈。**

[English](README.md) · [工程设计](docs/design.zh-CN.md) · [运行与改编](docs/walkthrough.zh-CN.md)

商家提出需求：“为新品做一个面向英国消费者的促销页面，配置配送和售后，保持克制的视觉风格。”

这句话背后，Agent 需要创建商品、关联素材、理解库存、配置配送、复用售后政策、建立促销，再让页面正确呈现这些能力。一个好看的页面不能证明商品可以买，创建成功的配送记录也未必覆盖目标地区。同时，它还要处理排版、素材构图、交互和修改反馈。

**如何把复杂业务系统，转化为 Agent 能够理解、探索、组合和验证的执行环境，使其在有限的上下文与执行预算下完成开放式目标？**

这是本项目探讨的核心。它源于 [Foundax](https://foundax.com)
的实践，同样适用于需要跨业务对象完成任务的 CRM、ERP、营销和运营软件。这里的 Agent-Native，是指业务能力可以被按需发现、通过普通代码组合，并通过明确的接口执行和验证。企业可以在既有业务服务之上建立这一层。

## 快速运行与体验

本仓库交付**设计文档、可运行的系统参考实现、合成业务数据和可改编的页面模板**。这些示例接口和业务规则用于教学参考，不映射 Foundax 的私有代码或真实数据模型。

环境要求：Node.js 22 或更新版本。无第三方依赖，无需安装 npm 包、模型密钥或 Foundax 账号。

在下载的仓库根目录运行：

```sh
npm run demo
```

打开终端输出的 `http://127.0.0.1:4317`。该命令会运行一段预设脚本：

1. 创建相互关联的商品、配送、促销和活动，故意选错配送政策。
2. 展示“配送政策存在，但未覆盖英国”的业务检查结果，随后修复引用。
3. 启动页面，通过 SDK 展示当前业务数据；点击演示下单，会按服务端价格计算金额并扣减模拟库存。

**这是确定性的流程演示，没有调用任何模型。** 原始数据、页面和写入结果保存在 `.local/` 目录。退出后可通过
`npm start` 恢复运行；如需重新运行演示脚本，需要指定新的 `BUSINESS_HOME`
目录，已有数据不会被重置。当前演示不包含真实的支付、税务、履约服务，也不会向公网发布网站。

准备让你的 Coding Agent 动手接入，请从 [TASK.zh-CN.md](TASK.zh-CN.md)
开始。任务入口使用同一套 SDK 和 CLI；可用的浏览器、视觉和 computer use 工具由你的 Agent 环境自行提供。

## 1. 复杂度应该放在哪里？

把海量的业务接口、数据库结构和设计要求全部塞进上下文，并不能自动构成一个可用的工作环境。模型仍然需要寻找入口、理解实体关系、处理字段转换，并在创作过程中维持这些信息。

固定工作流适合已知路径；离散工具适合边界明确的单一动作；而代码环境适合需要探索和组合的任务，这并不取代常规的 Tool
Calling，而是提供了不同的能力组织方式。在为 Coding Agent 设计环境时，核心在于如何分配这些职责：

| 设计问题                   | 本项目展示的做法                                                           |
| -------------------------- | -------------------------------------------------------------------------- |
| 业务对象如何创建与关联？   | 具名领域契约、显式 ID 引用、一次提交关联对象、宿主校验与版本前提。         |
| 如何减少无关信息的干扰？   | 先查询领域目录，再读取当前任务需要的契约和数据；提供处理历史信息的指引。   |
| 页面如何使用真实业务能力？ | SDK 返回组合后的活动视图，统一价格、优惠、配送、售后和媒体引用。           |
| 如何保留模型的创作空间？   | 使用普通 HTML/CSS/JavaScript，将业务规则留在服务端，页面仅负责构图和交互。 |
| 设计质量从何处获得支持？   | 模板附带设计意图与改编说明；素材附带构图和用途信息，并可直接查看。         |
| 如何验证结果与控制成本？   | 分离业务、代码和视觉的检查过程；仅针对发生变化的部分获取反馈。             |
| 如何向更多 Agent 开放？    | 内外部均调用同一套 SDK、CLI 和项目文件，不依赖特定模型的私有状态。         |

这些选择的共同目标是“把精力留给设计”。系统分担了规则校验与数据组装的负担，但不代表系统能够直接干预模型内部的 Attention 机制。

## 2. 职责边界与场景推导

```text
用户目标 → 内部或外部 Coding Agent
             ├─ 领域目录 → 按需读取契约、数据与素材
             ├─ SDK / CLI → 宿主校验 → 业务状态与版本控制
             └─ 模板说明 → 普通页面代码 → 浏览器观察与修改反馈
                                      ↓
                         SDK 活动视图与受控演示下单
```

参考实现中的 SDK 同时服务于 Node.js 和浏览器。业务视图在宿主端负责组合对象，并计算优惠价格；下单接口仅接受商品与数量等必要输入，不信任页面声称的成交金额。如果发生版本冲突（如数据已过期），宿主会拒绝覆盖并要求重新读取。

页面在加载或显式刷新时读取当前业务视图，不自动轮询；而订单记录会持久化保留成交时的模拟价格和售后条款。

这种机制明确了“系统该做什么，Agent 该做什么”。关于草稿状态、跨域写入、上下文生命周期与生产环境接入的详细推导，请参考[工程设计](docs/design.zh-CN.md)。

## 3. 本仓库的实现范围与限制

| 模块                     | 本仓库的实现范围                                                                                                |
| ------------------------ | --------------------------------------------------------------------------------------------------------------- |
| 业务宿主与 SDK/CLI       | 可运行。单店铺模式、领域写入、版本冲突处理、活动视图与模拟订单。（注：JSON 文件单进程写入不等于数据库事务能力） |
| 页面、模板与素材         | 可运行。提供普通浏览器代码、合成的 SVG 素材、设计意图与改编说明。                                               |
| 目录与按需披露           | 可运行。提供领域目录和分域读取。上下文由使用者或外部 Agent 选择读取，本包不自动加载或压缩上下文。               |
| 模型编排与上下文         | 设计说明与伪代码。本仓库不包含模型调用或内置的 Agent Loop。                                                     |
| 浏览器观察               | 提供真实预览入口和检查步骤；但不内置截图或 computer use 工具。                                                  |
| 编辑器、编译器与生产隔离 | 架构推演边界。本地服务不提供完整的编辑器、编译器、真实的身份认证、租户隔离或执行沙箱。                          |

本地进程采用单写入者模型，不应直接手工修改生成的 JSON 数据，也不要让多个进程共享同一个 `BUSINESS_HOME`
目录。该目录仅作为本地工作区，不是隔离边界。真实的商业支付、库存预留、重试幂等和生产发布，需要接入实际的业务服务中去完成。

## 4. 设计、性能与开放性

模板既提供代码，也解释场景目的和素材条件。SDK 的返回值直接包含业务语义（如已计算的优惠和配送规则），使得页面无需重复实现这些逻辑。

这些工程选择都伴随着取舍：[工程设计](docs/design.zh-CN.md)
详细讨论了复用与自由度、读取次数与上下文窗口大小、当前数据与历史状态、检查开销与反馈价值之间的平衡。

当工作环境被抽象为一个普通的代码项目时，开放 CLI 是一种自然的架构选择。外部 Coding
Agent 可以结合其自身的浏览器、视觉和 computer
use 能力继续工作。本仓库提供的 CLI 是独立的模拟教学接口，与 Foundax 商业版 CLI 相互独立。
